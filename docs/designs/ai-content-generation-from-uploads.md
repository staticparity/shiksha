## Problem Statement

Teachers currently build a topic's grading rubric by manually typing "key
concepts" one at a time into a form (`/teacher/setup`'s "Add a Topic" step —
concept + description pairs, added via a repeated "+ Add another" row). This
is slow and tedious, especially when the teacher already has real material —
notes, a textbook excerpt — that already contains everything the form is
asking them to retype.

## Demand Evidence

The real solo tutor already testing the enrollment-friction fix this week
directly complained that typing concepts manually is painful/slow. Not a
hypothetical — a stated frustration with the CURRENT form, from the actual
person using the product this week.

## Status Quo

`/teacher/setup`'s topic-creation form: teacher types a concept name and a
description of what a correct explanation looks like, row by row, with no
way to start from existing material. The `create_topic` API action
(`src/app/api/teacher/route.ts`) builds `knowledge_base = { key_concepts:
[...], common_misconceptions: [], difficulty_level: "intermediate" }` from
whatever rows the teacher filled in by hand.

## Target User & Narrowest Wedge

Same real solo tutor from the enrollment-friction design doc. What they'd
actually upload: "a mix of own notes and textbook/PDF excerpts" — their own
prep material, not a formal, clean document.

Narrowest wedge: add a "generate from content" step that pre-fills the
EXISTING concept-editing rows from pasted text. Don't change the submission
format. Don't remove the manual path (some topics genuinely won't have
source material to paste). Don't build a document-parsing pipeline — meaning
no OCR/complex-layout extraction infrastructure (Textract-class tooling);
basic PDF-to-text conversion, if v1 supports PDF at all, is a different,
much smaller thing than what that wedge line rules out (see Open Questions).
v1 is creation-time only — regenerating concepts on an already-created topic
is a deliberate exclusion, not an oversight; a teacher who wants to change
an existing topic's concepts still uses the existing manual edit path.

## Constraints

- Content is a mix of typed notes and textbook/PDF excerpts — plain-text
  paste is the confirmed baseline; whether v1 also needs real file (PDF)
  upload vs. paste-only is an open question below.
- Output must slot into the EXISTING `knowledge_base`/`key_concepts` shape
  so nothing downstream (Learner Agent prompting, Wisdom Agent grading,
  misconception detection) needs to change. Generation populates
  `key_concepts` only — `common_misconceptions` and `difficulty_level` stay
  at their current defaults ([] and "intermediate"), unchanged by this
  feature.
- Merge behavior: "Generate from content" REPLACES the current concept rows
  wholesale, not an append or fill-only-empty-rows merge — one clear action,
  not a partial-merge the teacher has to reason about row by row. Confirm
  step triggers if ANY row has non-empty concept or description text (a
  single untouched blank default row does not count as "typed").
- Bound the input: cap pasted content at ~8,000 characters (enforced
  server-side, not just a client-side message) with a floor of ~50
  characters below which "Generate" stays disabled — a few-word paste isn't
  worth a round trip. Output is capped at 8 concepts with no enforced
  minimum (see Approach A) so the LLM call has a defined cost ceiling
  without forcing padding on thin content.
- Show a loading state on the "Generate" action and a clear error state if
  the call fails — this is a new network/LLM round trip, not a form-only
  interaction.
- Data handling: pasted content goes to OpenAI via the same integration
  already used for every teach-back session (Learner/Evaluator/Wisdom
  agents already send student conversation content the same way) — no new
  data-handling posture is being introduced, but the teacher-facing copy
  should say the pasted text is sent to the AI, same as it would for any
  other Shiksha AI feature.
- The teacher must review before anything enters the actual grading rubric
  a real student gets scored against — non-negotiable. Shiksha's whole
  premise is honest, ungameable assessment; an unreviewed AI-generated
  rubric cuts directly against that identity, not just a minor UX risk.

## Premises

1. The pain is real but moderate — time/annoyance from manual typing, not a
   coverage/adoption blocker like enrollment friction was. Confirmed: "just
   time/annoyance, not a coverage problem."
2. A direct LLM call is the right mechanism — no dedicated document-parsing
   vendor needed. Landscape check confirmed enterprise document-AI tooling
   (Textract, Azure Document Intelligence, ABBYY) solves a different, harder
   problem (high-volume, complex-layout, audit-grade extraction) than a
   solo tutor pasting a chapter of notes for one topic at a time.
3. The output should slot into the existing `knowledge_base` shape so
   nothing downstream needs to change.
4. Genuinely pre-product for this sub-feature specifically — reasoning from
   the tutor's stated frustration with the current form, not from a direct
   request for this exact solution.

## Approaches Considered

### Approach A: Generate then edit (CHOSEN)
Teacher pastes content on the topic-creation form. A "Generate from content"
step sends it to a new, small LLM call (same pattern as the existing
Learner/Evaluator/Wisdom agents) that drafts `key_concepts`, pre-filling the
SAME concept-editing rows that already exist today. Teacher reviews/edits
before hitting "Add Topic" — the final submission format is unchanged.

**Route:** a new, dedicated route (`/api/teacher/generate-concepts`), not a
5th action inside the existing `teacher/route.ts` dispatcher. (Resolved
during /plan-eng-review's outside-voice pass: the original justification —
"avoids duplicating the auth check" — was wrong, since that check already
runs once for all 4 existing actions with zero duplication either way. The
real, independent reason to split is keeping AI-generation's error/retry/
timeout semantics and its own test-mocking style out of an otherwise pure-
CRUD dispatcher, matching how `/api/mastery` already handles its one
AI-generation job as a dedicated route rather than folding it into a
shared handler. Each route keeps its own simple inline auth check — no
shared `verifyTeacher()` helper, since there's no real duplication to
solve.)

**Model:** `gpt-4o-mini` — structured extraction from text is closer to the
Evaluator Agent's per-turn structured judgment than the Wisdom Agent's
end-of-session holistic grading; matches the existing cost-effective tier
for frequent, structurally simple calls. Not a reasoning model, so no
latency-regression risk (the exact pitfall already caught and fixed
elsewhere this session with the Evaluator Agent).

Minimal contract: `POST /api/teacher/generate-concepts` taking `{ content:
string }` (server-side re-validates the ~8,000-character cap — the
client-side message is UX, not the enforcement boundary), returning
structured output shaped as `{ key_concepts: [{ concept: string,
description: string, sourceExcerpt: string }] }` via `generateObject`'s
structured-output mode (same generation pattern already used by the Wisdom
Agent, not free-text-then-regex-parse), capped at 8 items with a floor of
0 — content that only genuinely supports 1-2 concepts returns 1-2, never
padded to hit an artificial floor, and content with nothing extractable
(off-topic paste) returns an empty array, which the UI shows as "Couldn't
find clear concepts in that — try different content or add them manually"
rather than a silent empty table, WITHOUT clearing any rows the teacher had
already confirmed replacing — an empty or failed generation always restores
whatever was there before, never leaves the teacher with nothing. This
resolves the tension between "cap the output" and "only draw what's
genuinely present": the cap is a ceiling, not a target.

Retry/timeout: use `generateObject`'s own built-in `maxRetries: 1` and
`timeout: 30_000` options (verified present on the installed `ai@6.0.152`
package's `CallSettings` type during /plan-eng-review) instead of hand-rolled
retry logic. On exhausted retries or any error, surface a clear message and
preserve whatever the teacher had already typed manually before clicking
Generate — never wipe existing rows on failure. The "Generate" button
disables while a request is in flight (same pattern as the existing form's
submit-button loading state) to prevent double-submit.

Grounding — reframed after /plan-eng-review's outside-voice pass caught a
real logical gap: a `sourceExcerpt` field + case-insensitive substring
match against the pasted content can only verify that SOME fragment of text
appears in the source — it cannot verify that the substantive claim built
around that fragment is actually true or supported. A model could attach a
genuine, true, generic quoted word to a fabricated mechanism and pass this
check cleanly. This mechanism is kept (it's still useful — showing the
tutor roughly where a concept came from speeds up their review) but is NOT
a fabrication safety net, and neither the code nor any UI copy should claim
otherwise. The human review step is the only real safety net for
fabrication; this excerpt is a review AID, not a review REPLACEMENT.
Normalize whitespace and smart-quotes/unicode punctuation before the
substring check (both source and excerpt) — PDF-extracted text routinely
has formatting drift that would otherwise false-flag genuinely grounded
concepts as unverified.

Effort: S/M. Risk: Low — a bad AI draft is just as editable as a blank form;
nothing enters the grading rubric without the teacher seeing it first.
Reuses 100% of the existing concept-editing UI (`concepts` state,
`addConcept`/`updateConcept`/`removeConcept`) and the `create_topic`
action/`knowledge_base` shape.

Explicitly out of scope for v1: any rate-limit/abuse cap across repeated
Generate clicks or across topics. At solo-tutor volume (one person, a
handful of topics) the realistic abuse surface is negligible; revisit if
this ever opens to a context with many teachers hitting it concurrently.

### Approach B: Fully automated — not chosen
Upload content, AI extracts concepts, the topic gets created directly with
no review step. Fastest, genuine "wow" factor, but no human check before
AI-generated content becomes the actual grading rubric a real student is
scored against — directly in tension with Shiksha's own honesty premise.
Rejected on product-identity grounds, not just risk-aversion.

### Approach C: Chat-based concept refinement — deferred
A conversational interface (matching the student-facing teach-back chat
pattern) where the teacher iteratively refines the concept list by talking
to the AI instead of editing form fields. Novel, matches Shiksha's
conversational identity (Pip already exists), but meaningfully bigger build
(L/XL) for a pain point already established as moderate, not urgent.
Deferred, not ruled out — worth reconsidering if Approach A's real use
reveals teachers wanting more back-and-forth than one-shot generation gives.

## Recommended Approach

Approach A. Matches the actual stakes (moderate pain → small, low-risk
effort), preserves the human-review step the product's honesty identity
depends on, and reuses the maximum amount of already-working code.

## Open Questions

All three resolved during /plan-eng-review (2026-08-25):

- **File format scope for v1:** plain-text paste only. PDF upload deferred —
  copying text out of a PDF is a standard, near-zero-friction action,
  nothing like the tedium of typing structured form rows the feature
  actually targets. Keeps the S/M effort estimate honest.
- **Route/agent placement:** `/api/teacher/generate-concepts`, a new
  dedicated route (see Approach A) — resolved with a correction along the
  way (see Approach A's route note): the original "avoids auth-check
  duplication" justification was wrong, caught by the outside-voice pass.
- **Model/cost choice:** `gpt-4o-mini` (see Approach A).

## Success Criteria

The tutor pastes real content for a real topic (not a demo) and keeps at
least half the generated concepts with only minor edits (wording, not
wholesale rewrites) rather than deleting most of them and typing their own
from scratch. This is judged directly by watching the real use (same
"watch, don't demo" discipline as the enrollment-friction test) — not an
automated metric. If that bar isn't hit on the first real use, that's a
signal the extraction quality or prompt needs work before calling this
validated, not a reason to declare success anyway.

## Dependencies

None blocking. Builds on the existing `create_topic` action, the existing
`ai` SDK/OpenAI integration already powering the Learner/Evaluator/Wisdom
agents, and the existing concept-editing UI. No new distribution channel —
ships as part of the existing Shiksha web app on the existing deploy
pipeline.

## The Assignment

Next time you add a real topic — not a demo one — paste in your own actual
notes for it and check honestly whether the generated concepts are
something you'd actually keep. Don't build this speculatively and hope it
works; use it on real material before handing anything to the tutor.
