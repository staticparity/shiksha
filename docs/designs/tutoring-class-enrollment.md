## Problem Statement

Shiksha's existing student onboarding assumes an institutional multi-class context:
each student independently creates their own account (email + password) before a
teacher can enroll them in a class. That model doesn't fit a solo tutor running a
small tutoring class (5-20 students) who personally manages enrollment — self-serve
signup is friction the tutor has to push onto students (or their parents) before
anyone can use the product at all.

## Demand Evidence

None yet, and that's stated plainly rather than papered over. This is inferred need
— reasoning from how a solo tutoring class actually operates, not a direct request.
There IS a specific, real tutoring class (solo tutor, small group) the founder can
put a working version in front of this week, which is the actual test.

## Status Quo

The target tutoring class currently checks understanding with written tests/quizzes
— the traditional recall-based assessment Shiksha's whole premise (Feynman
teach-back, can't be gamed by memorization) is built to replace. This is a
coherent, real pain point even without a direct customer ask: it's the same gap
the two-axis diagnostic work (shipped in a prior session) already targets, just
confirmed against a concrete small-tutor context instead of a hypothetical school.

## Target User & Narrowest Wedge

A solo tutor teaching a small group (5-20 students), personally responsible for
every student's results, who already knows each student individually — unlike a
school-scale teacher managing dozens of students across multiple classes.

Narrowest wedge: don't touch the diagnostic engine, the dashboard, or the alerts —
all confirmed still valuable at this scale (see Premises). Fix the one concrete
adoption barrier: let the tutor enroll students directly instead of requiring each
student to self-signup first.

## Premises

1. The diagnostic/dashboard machinery already built (per-student two-axis
   breakdown, red-flag alerts, class-wide heatmap) is valuable even for a solo
   tutor with 5-20 students — REVISED from an initial assumption that a solo
   tutor wouldn't need class-wide aggregation. Founder disagreed and specified all
   three elements (breakdown, alerts, heatmap) still matter, even at small scale.
2. The actual adoption barrier is elsewhere: per-student self-signup (each
   student independently creating an email+password account before the tutor can
   enroll them) is real friction for a tutor managing enrollment themselves,
   especially with younger students who may not have independent email access.
3. Shiksha's terminology and structure (School → Class → Topic, separate teacher
   and student portals, teacher invites by email) was built for an institutional
   multi-class context. It may not map naturally onto "my tutoring batch" as a
   mental model, even though the underlying *schema* (tables, relationships)
   doesn't need to change for this pass — the auth *trigger behavior*
   (`handle_new_user()`) is a separate question, flagged below, not covered by
   this premise.
4. This is genuinely pre-product for this use case — no direct customer ask yet —
   but there's a real, specific tutoring class available to test with this week,
   which is the actual validation step, not more design work.

## Approaches Considered

### Approach A: Fix enrollment friction only
Let the tutor add students directly (name + email, no self-signup step required)
instead of requiring each student to create their own account first. Email stays
required, not optional — Supabase auth needs a unique identifier per student, and
"name-only" enrollment would mean inventing a non-Supabase-auth student concept,
which is real added complexity, not a small variation. What changes is *who*
provides the email and *when*: the tutor supplies it up front (a parent's email
for younger students is a reasonable answer, though not resolved here — see Open
Questions) rather than the student self-registering before enrollment can happen.
Effort: S/M. Risk: Low-to-Medium (see Open Questions — the auth trigger path is
the one piece of real uncertainty). Reuses the existing school/class/topic
*schema*, teacher and student portals, and enrollment RPC pattern; the signup
*trigger* behavior is the one part not yet confirmed unchanged. The existing
self-signup path must keep working alongside this — this adds a second enrollment
path, it doesn't replace the first, since institutional users still need it.

### Approach B: Tutor mode (onboarding + language + WhatsApp share) — not chosen now
Simplified solo-tutor onboarding ("Add your students" instead of School → Class →
Invite), tutor-created student accounts, "My Students" language instead of
"School/Class" in this mode, plus a WhatsApp-shareable link per topic (a direct
callback to the original Pip prototype, which was itself extracted from a WhatsApp
conversation). Addresses both identified frictions (enrollment AND institutional
terminology) but bigger scope before any real validation exists. Rejected for now
— not ruled out, deferred pending what Approach A's real-world test reveals.

### Approach C: No student accounts at all (tutor-supervised sessions) — not chosen
Students never log in; the tutor picks a name from their roster and hands off a
device or link per session, matching how in-person small-group tutoring actually
happens. Removes signup friction entirely but requires reworking how sessions
attach to a student_id (currently tied to a real authenticated Supabase user) and
weakens the streak/credit motivational layer, since students wouldn't own a
persistent login. Rejected: architectural risk disproportionate to a still-
unvalidated bet.

## Recommended Approach

Approach A. Matches the narrowest-wedge principle and the landscape finding (pilot
one thing, measure one outcome) — ships fast enough to get in front of the real
tutor this week, targets the one concretely-identified friction point, and leaves
the bigger terminology/WhatsApp bet (Approach B) for if and when Approach A's test
shows it's actually needed.

## Open Questions

- **Blocking:** exact enrollment UX for Approach A — does the tutor set a
  temporary password the student changes on first login, or does Shiksha send a
  magic link? Also needs to cover how the tutor conveys that credential to the
  student (or parent) in the first place — not just which mechanism Shiksha
  uses internally. This is the mechanism the whole approach depends on; not a
  minor detail deferred to later, it needs resolving before effort/risk can be
  confirmed. Appropriate for /plan-eng-review to decide, not this doc. Resolve
  together with the minor/parent-email question below — a magic link a parent
  has to relay to the student every session partially reintroduces the friction
  this design is meant to remove.
- **Blocking:** whether `handle_new_user()` and the school-domain-matching trigger
  (built for the self-signup flow) need to change when the tutor creates the
  account instead of the student, and whether the two enrollment paths
  (self-signup + tutor-created) can coexist without collision.
- Whose email, when a student is a minor without independent access — a parent's
  email is the likely answer but isn't decided here; flagged, not resolved. Any
  consent/privacy consideration for a tutor creating an account on a minor's
  behalf is a real question this doc raises but doesn't answer.
- Duplicate handling: what happens if a student who already self-signed-up
  (institutional flow) gets added again by a tutor? Not addressed — punt to
  /plan-eng-review.
- Roster capacity/editing: whether the enrollment UI should enforce the 5-20
  range this doc uses to characterize the target user (it's a description of who
  this is for, not a hard limit), and how a tutor removes or corrects a
  wrongly-added student. Out of scope for this pass; noted so it isn't silently
  dropped.

## Success Criteria

The real tutor can enroll their actual students without any of those students
needing to self-signup first, and completes at least one real teach-back session
end to end with a real student this week.

## Dependencies

No external dependencies (no new vendor, no new infra). Internally, this is
blocked on resolving the two "Blocking" Open Questions above (enrollment
mechanism, auth trigger behavior) before implementation — those aren't
follow-up polish, they're prerequisites /plan-eng-review needs to settle first.
Otherwise builds directly on the existing school/class/topic schema, teacher
portal, and Supabase auth setup already shipped.
